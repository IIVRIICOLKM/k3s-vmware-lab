## 주요 결과

**K3s 실습 (제안서 8번 슬라이드)**

- 노드 4대 Ready: VM 3대(Rocky 9.8)와 물리 호스트(Ubuntu 26.04, RTX 3090)
- 작업 배치:
  - gpu-host에 `nvidia.com/gpu=present:NoSchedule` taint를 걸었다.
  - GPU 파드는 gpu-host에서만 RTX 3090을 인식했다. GPU가 1개뿐이라 두 번째 GPU 파드는 `Insufficient nvidia.com/gpu`로 Pending이 됐다.
  - 일반 파드 4개는 gpu-host를 피해 배치됐다.
- 복제본 1 → 3: 요청 60개가 세 파드로 나뉘었다.
- 파드 강제 삭제: 2초 뒤 새 파드로 복구됐다. 컨테이너 종료: 같은 파드에서 RESTARTS가 1이 됐다.
- 노드 중단(worker-cpu-2 강제 종료):
  - 44초 뒤 NotReady가 됐다.
  - 그 뒤 308초 만에 파드가 다른 노드에서 Ready가 됐다. 대부분은 기본 toleration 300초다.
  - `entry.sh`로 복구한 뒤 다시 Ready가 됐다.
  - 노드가 돌아와도 파드를 원래 노드로 되돌리지는 않았다(자동 재균형 없음).

**학습 Job (제안서 11·15번)**

- 2 에폭 체크포인트가 생긴 뒤 파드를 삭제했다. 파드는 SIGTERM을 받고 그 시점(4 에폭 1번째 스텝)의 `ckpt-e0004-s00001.pt`를 남긴 뒤 `INTERRUPTED`로 끝났다.
- Job이 새 파드로 다시 시도했고, 새 파드는 그 체크포인트에서 이어서 학습해(`resumed_from`) GPU(cuda)에서 `DONE`이 됐다.
- 이미 `DONE`인 작업 번호로 다시 요청하면 학습하지 않고 기존 상태를 돌려줬다(중복 실행 방지).
- 로컬(CPU) 비교: 끊었다가 이어서 학습한 모델이 한 번에 학습한 모델과 비트 단위로 같았다.

**추론 워커 (제안서 10·14번)**

## 일정 재조정

- **3~4주차(9/21~10/4)는 진행이 없었다.** 시험 기간이 겹쳤다. 그래서 2–4주차 항목인 호스트 노드 등록이 10/6로 밀렸다.
- **10/15~10/30에는 클러스터가 멈춰 있었다.**
  - 커널 업데이트(7.0.0-38)로 VMware 커널 모듈이 빠지면서 VM이 뜨지 않았다(10/1에 이어 두 번째).
  - 콘솔에서 모듈을 다시 빌드한 뒤 복구했다.
  - 이 기간에는 클러스터가 필요 없는 작업(학습 스크립트, Helm 차트, 빌드·실습 스크립트)을 먼저 진행했다.
- **그 결과 4–8주차 항목을 10/30에 몰아서 실행·검증했다.** 9주차부터는 원래 일정(MySQL 연동, 추론 워커 GPU 경로)으로 돌아간다.

## 문제와 대응 (이번 주 발견)

1. **ConfigMap 빌드 컨텍스트가 심볼릭 링크로 들어감.** `train-worker:v0.1`에 `train.py`가 깨진 링크로 들어갔다. 빌드 전에 실제 파일로 복사하게 고치고, push 뒤 레이어 검사를 추가했다. v0.1은 삭제했다.
2. **GPU에서 재개할 때 난수 상태 복원 실패.** `torch.load(map_location=cuda)`가 원인이었다. CPU로 읽게 고쳤다. v0.2는 삭제하고 v0.3을 쓴다. 실패했던 Job도 v0.3으로 남은 체크포인트에서 이어서 끝냈다.
3. **k3s-agent 재시작 직후 GPU 할당 경합.** 스모크 테스트가 `nvidia.com/gpu Available: 0`으로 거부됐다. 재시도를 넣었고, 플러그인 준비 대기와 실패를 바로 감지하는 대기 방식으로 바꿨다(10분 대기 → 10초).
4. **롤링 재배포 때 종료된 파드로 연결이 감.** 벤치마크 중 요청 일부가 멈췄다. 추론 Deployment에 `preStop sleep 5`를 넣고, curl에 제한 시간을 뒀다.
5. **Ubuntu 26.04 호스트 특성.** sudo-rs 프롬프트 문제는 `sudo.ws`로 해결했다. HashiCorp apt 키 교체 문제는 NVIDIA 저장소만 갱신하게 해서 피했다.
