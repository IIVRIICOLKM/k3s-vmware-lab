## 2. 계획과 달라진 점

1. **F7: "동시 150"은 실제 연결이 아니었다.** 설정 동시 수 150에 실제 최대 연결은 25개였고, 워커의 HTTP 스레드 풀(큐 20 + 스레드 1×배치 4 + 16 = 40)이 한도가 아니었다. 429는 큐(용량 20)가 넘쳐서 났다. 보고서에는 요청 수, 설정한 동시 수, 실제 연결 수를 따로 적었다.
2. **F7: 큐 길이 게이지는 1차 근거로 쓰지 않았다.** Prometheus(5초 수집)의 최댓값은 16으로 0.2초 샘플(20)보다 작았다. 클라이언트 쪽 코드별 개수를 1차 근거로 썼다. Prometheus `increase()`는 외삽이라 실제 개수와 다르다(ok 114 vs 101).
3. **F8: 롤백 시간 0.3초의 의미가 계획과 다르다.** 계획은 "롤백 시간"을 새 파드가 뜨는 시간처럼 읽을 수 있게 적었지만, CPU 배포에서는 예전 파드가 계속 Ready라서 설정만 되돌린 시간이다. 예전 파드가 없는 상황(GPU 변형)은 이 숫자로 알 수 없다.
4. **F1: 판정 기준 "60초 이내"가 너무 느슨했다.** 실측 1.4초(작은 모델, 이미지가 노드에 있음). 큰 모델·GPU는 다를 것이다. CPU 변형은 두세 번 더 재서 기준을 정한다(제안: 10초 안팎).
5. 계획의 "예상"과 달리 F1에서 서비스가 끊긴 시간은 요청 한두 번 사이(실패 1개)였다. 원인(연결 거부·끊김)은 확인하지 못했다.
6. `--prom`의 실제 값은 `monitoring/prometheus:9090`이다(계획 문서의 예시 `prometheus-server:80`은 틀렸다). 계획 문서 11절과 상태 줄을 고쳤다.

## 3. `scripts/fault-test.sh`에서 바꾼 줄과 이유

| 위치 | 바꾼 것 | 이유 |
|---|---|---|
| `load_job` (1497행~) | 부하 Job 안에서 `/proc/net/tcp`의 원격 포트 8080 ESTABLISHED·SYN_SENT를 0.1초마다 세고 끝에 `N <측정 횟수> <최대 ESTABLISHED> <최대 SYN_SENT>` 한 줄을 출력(1521행 `csampler`) | 관측이 찾은 대로 "동시 N"은 설정값이고 실제 연결이 더 적다. 실제로 연 연결 수를 따로 적어야 한다 |
| `conn_sampler_start` / `conn_sampler_stop` (1461, 1469행, 새 함수) | 추론 파드 안에서 0.2초마다 `/proc/net/tcp`를 읽는 `kubectl exec` 스트림을 부하 내내 열고, 서버 쪽 최대 ESTABLISHED를 계산 | 서버가 실제로 받은 연결 수. `kubectl`을 직접 불러 `kill`이 스트림을 닫게 했다(함수를 거치면 `$!`가 서브셸이다) |
| `ci_pods_block` (1484행, 새 함수) | `ci` 네임스페이스 파드와 `kubectl top node gpu-host`를 보고서에 남김 | Jenkins 에이전트의 gpu-host CPU 사용이 부하 시험에 영향을 줄 수 있다. F7은 부하 직전·직후(1563, 1568행), F8·F1은 실험 시작(776, 1684행) |
| `run_overload` (1539행~) | 보고서에 요청 수 / 설정 동시 수 / 실제 연결 수 / HTTP 스레드 풀(40)을 따로 적음. 큐 길이 지표 이름에 "보조 근거" 설명 추가. 부하 Job이 끝나지 않아도 샘플러를 닫도록 처리 | 같은 이유 |
| `show_plan` F7 (679~680행) | `--dry-run`의 "측정" 줄에 새 항목 추가 | 설명과 동작을 맞춘다 |

- 새 `awk` 필터는 가짜 `/proc/net/tcp` 입력으로 확인했다(서버 2, 클라이언트 2/1). 실제 실행(F7)에서 서버 쪽 25 = 클라이언트 쪽 25로 일치했다. `bash -n`과 `scripts/verify-project.sh`(필수 파일 135개, 문법 OK)가 통과했다.
- 나머지(F2~F6, `cleanup`, `--dry-run` 출력 전체)는 1단계 그대로다. 이번에 바꾸지 않았다.

## 4. 14주차(F6, F4, GPU 실험)로 넘길 것

- **승인된 조건 / 남은 실험:** F6 `registry-down`(Jenkins·Kaniko 빌드가 없는 시간을 총괄이 정해 준다), F4 `mysql-down`(진행 중인 작업이 없는 시간), F5 `gpu-busy`, F2 `train-kill`, F1·F8의 GPU 변형(`--gpu 1`), F3 `node-stop`(worker-cpu-2에 Argo CD가 있어 나중에 따로 정함). F2·F4가 `docs/labs/train-resume-*`, `job-db-*`를 새로 쓰는 것은 승인됨(기존 보고서는 덮어쓰지 않는다).
- **F1 `--mode graceful`**은 이번에 하지 않았다(총괄 지시). 14주에 SIGTERM + preStop 5초 경로를 잰다.
- **F1 CPU 반복:** 복구 시간은 1회 값이다. 두세 번 더 재서 판정 기준(10초 안팎)을 정한다.
- **F1·F8 GPU 변형:** GPU는 예전 컨테이너가 쥔 채로 새 파드가 뜰 때의 Pending·배정 실패, `maxSurge 0`으로 서비스가 끊기는지 확인한다. F8 GPU는 롤백 시간 해석이 달라진다(예전 파드가 없다). 한 번에 하나, GPU 승인 필요.
- **F7 확장(선택):** 이번에는 큐 20·배치 4·스레드 1 한 조건뿐이다. 스레드 풀(40)이 한도가 되는 더 센 부하는 모니터링 보고서 9.3절 7번의 추정을 확인하는 일이라 범위를 정해야 한다.
- **측정 방법 메모:** 큐 길이 게이지는 짧은 포화를 놓치니 코드별 개수를 1차 근거로 쓴다. 실제 연결 수는 `load_job`·`conn_sampler`가 이제 같이 남긴다. 시작 때 `ci` 파드를 보고서에 남기므로 CICD_연결의 Jenkins 빌드가 시작되면 보고서에서 겹침 여부를 볼 수 있다.
- **지연 p50/p95:** 워커가 히스토그램 버킷을 내보내지 않아 지금은 평균만 본다(모니터링 보고서 9.3절 9번). F1·F7의 "응답 시간"은 클라이언트가 잰 값이다.
- **문서:** `docs/plan-week13-verification.md`의 6절 일정·실행 결과 반영은 14주 정리 때 한꺼번에 한다.
