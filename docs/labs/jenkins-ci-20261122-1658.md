## 6. 에이전트 파드 자원 (실제 값)

`Jenkinsfile`의 파드 정의와 15초 간격 `kubectl top` 표본(위 5절)이다. 에이전트는 항상 하나만 뜨고(`disableConcurrentBuilds`), 모두 gpu-host에 배정됐고, `nvidia.com/gpu`는 요청하지 않는다.

| 파드 | 컨테이너 | CPU 요청 | 메모리 요청 | 메모리 한도 | 합계(요청) | 관측 최대 (표본) |
|---|---|---|---|---|---|---|
| 검사 파드 | jnlp / gcc / torch | 50m / 500m / 500m | 128Mi / 512Mi / 512Mi | 384Mi / 2Gi / 2Gi | CPU 1050m, 메모리 1152Mi | 658Mi (파드 합계) |
| 빌드 파드 (이미지마다 1개씩) | jnlp / kaniko / tools | 50m / 1 / 50m | 128Mi / 2Gi / 64Mi | 384Mi / 8Gi / 256Mi | CPU 1100m, 메모리 2240Mi | 363Mi (파드 합계) |
| 컨트롤러 `jenkins-0` (worker-cpu-1) | jenkins | 250m | 768Mi | 1Gi | – | 606Mi |

- 컨트롤러의 `-Xmx512m`와 메모리 한도 1Gi는 승인안 그대로다. 바꾼 것은 시작할 때만 도는 init 컨테이너(플러그인 설치)의 한도뿐이다: 768Mi → 1Gi, 힙 `-Xmx512m` 지정. 요청(256Mi)은 그대로라 스케줄링에는 영향이 없다.
- 보안 설정: 파드 전체에 seccomp `RuntimeDefault`, 컨테이너마다 `privileged: false`와 `allowPrivilegeEscalation: false`, 추가 capability 없음. AppArmor `Unconfined`는 `gcc` 컨테이너 하나에만 줬다 (8절).
- 시간: 빌드 #5(검사 4단계 + 이미지 2개 + 결과 기록)는 시험 스크립트 로그 기준 16:58:38 → 17:02:30, 약 3분 50초였다. 베이스 이미지(gcc, PyTorch, CUDA)가 gpu-host에 이미 받아져 있을 때의 시간이다. 처음 배포하면서 받을 때는 이미지 단계에 더 걸린다.
- 컨트롤러 첫 시작(플러그인 73개 내려받기)은 약 10분 걸렸다 (계획한 3~6분보다 길다).

## 8. gpu-host AppArmor (시험 중 찾은 제약)

C++ 단계의 "워커를 띄우고 SIGTERM으로 끝내 보는" 시험이 처음에 `scripts/jenkins-stage-cpp.sh: line 119: kill: (84) - Permission denied`로 실패했다 (빌드 #2).
디버그 파드(삭제함)에서 같은 `gcc` 이미지를 gpu-host에 두 가지로 띄워 확인했다.

| 프로파일 | `kill -0` | `kill -TERM` | `kill -KILL` | `kill -USR1` |
|---|---|---|---|---|
| 기본 (`cri-containerd.apparmor.d//&unconfined`) | 됨 | EPERM | EPERM | EPERM |
| `appArmorProfile: Unconfined` | 됨 | 됨 | 됨 | 됨 |

기본 프로파일에서도 root이고 `CAP_KILL`이 있다(`CapEff 0xa80425fb`, seccomp 꺼짐). 총괄 승인(A안)으로 `gcc` 컨테이너 하나에만 `Unconfined`를 줬고 그 뒤 C++ 단계가 통과했다 (빌드 #3부터).
`torch`(Python) 컨테이너는 같은 증상이 나지 않았다 (`[python] PASS: Ran 37 tests`), 그래서 기본 프로파일 그대로다. 대안 C(gpu-host에 신호를 허용하는 `Localhost` 프로파일)는 호스트 변경과 sudo가 필요해 하지 않았다 (사용자 결정 사항).
**플랫폼·검증이 알아 둘 것**: 컨테이너 안에서 자식 프로세스에 신호를 보내는 파드(`kill`, `timeout`, 셸 `trap` 정리, 신호 전달 init)는 gpu-host에서 같은 이유로 실패할 수 있다. VM 노드(Rocky)는 이번에 확인하지 않았다. 자세한 설명: `infra/k8s/jenkins/README.md` "gpu-host의 AppArmor".

## 9. 발견한 결함 (이번 범위 밖이라 고치지 않음)

## 11. 결과 전달 (CICD_연결 / Argo CD가 읽는 값)

- 이미지: `registry.k3slab.local:5000/infer-worker:<태그>`, `registry.k3slab.local:5000/train-worker:<태그>`. 태그는 덮어쓰지 않는다(이미 있으면 다시 빌드하지 않고 같은 digest를 쓴다, 3절).

- 어디서 읽나: ConfigMap `ci/ci-latest`(운영 작업) 또는 `ci/ci-latest-local`(시험 작업). 키는 `tag`, `commit`, `source`, `build`, `build_url`, `built_at`, `infer-worker.digest`, `infer-worker.ref`, `train-worker.digest`, `train-worker.ref`, `result.json`. 같은 내용이 Jenkins 빌드 산출물 `ci-result.json`에도 있다 (2절 예시).
